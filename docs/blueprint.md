# Link MAP：プロジェクト設計指針（Blueprint）

## 1. プロジェクト概要
ユーザーが複数の「作品世界（World）」を管理し、その中の実体と関係性をグラフ構造で可視化・編集する創作支援エディタ。「点（Entity）」と「線（Connection）」の組み合わせにより、複雑な物語の相関図を動的に構築する。

## 2. コア思想：Everything is a Connection
情報の重複を排除し、かつ柔軟な拡張性を持たせるため、以下の設計思想を徹底する。

- **Entities（実体）の極小化**: Entityテーブルは名前と識別子のみを持つ。その他の属性は持たせない。
- **Connections（関係性）への集約**: あらゆる属性、エピソード、因縁は、すべてConnectionテーブルに集約する。
- **自己参照プロフィール (The Heart of the System)**:
  - `from_id` と `to_id` が同一のConnectionを「詳細・プロフィール」として定義する。
  - 「自分自身との関係」が「自分自身の説明」となるデータモデルを実現する。

---

## 3. フロントエンドアーキテクチャ：関心の分離とカプセル化

本プロジェクトは、保守性・拡張性・開発体験を最大化するため、厳密な関心の分離に基づいたアーキテクチャを採用する。

### A. 全体構造

`src` ディレクトリ配下は、以下の責務を持つモジュールで構成される。

| ディレクトリ     | 責務                                                               | 詳細                                                                                                             |
| ---------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `components`     | **UIの描画**                                                       | 状態を持たない純粋な見た目とユーザー操作の伝達に特化する。                                                       |
| `hooks`          | **ビジネスロジックと状態管理**                                     | 再利用可能なロジックをカプセル化し、UIから状態管理ライブラリやAPIを隠蔽する。                                        |
| `contexts`       | **グローバルな状態と機能の提供**                                   | アプリケーション全体で共有される状態と、それを操作するためのインターフェース（フック）を集約・提供するハブ。         |
| `pages`          | **ページの構成**                                                   | 各ルートに対応するコンポーネント。主に `components` を組み合わせてページをレイアウトする。                       |
| `routes`         | **ルーティング定義**                                               | アプリケーションのURL構造と、それに対応するページコンポーネントおよびレイアウトを定義する。                      |
| `utils`          | **純粋な補助関数**                                                 | 状態やUIに依存しない、単一責務の汎用関数（バリデーション、データフォーマットなど）を配置する。                     |
| `lib`, `theme`.. | **設定・ライブラリ**                                               | SupabaseクライアントやUIテーマなど、プロジェクト全体を支える基盤設定。                                           |

### B. Hooksの設計思想：Facadeパターンによるカプセル化

**カスタムフックは、機能の「公開窓口（Facade）」としての役割を担う。**

- **内部実装の隠蔽**:
  - `src/hooks/useAuth` のように、機能単位でディレクトリを作成する。
  - `useAuthState.ts` や `useAuthForm.ts` のような詳細なロジックは、このディレクトリの**内部に留める**。
  - `useAuth.ts` ですべての内部ロジックを合成し、コンポーネントが利用するための単一でシンプルなインターフェースを提供する。

- **公開APIの限定**:
  - `src/hooks/index.ts`（バレルファイル）では、`useAuth` のような**公開フックのみをエクスポートする**。
  - これにより、コンポーネント開発者は内部実装を意識する必要がなくなり、意図しない方法での利用を防ぐ。

### C. ルーティング設計：Nested Routesによるレイアウト管理

**`react-router-dom` のネストされたルート（Nested Routes）と `<Outlet />` を全面的に採用する。**

- **共通レイアウトの集約**:
  - `/dashboard` 以下の全ページに共通するサイドバーやヘッダーは、`DashboardLayout.tsx` に集約する。
  - ルーティング定義 (`router.tsx`) では、`DashboardLayout` を親ルートの `element` として設定する。
- **宣言的な親子関係**:
  - 子ルート（例：`<Route index element={<WorldSelector />} />`）は、親の `<Outlet />` に描画される。
  - これにより、「どのレイアウト」の中に「どのページコンテンツ」が表示されるかという構造が、ルーティング定義を見るだけで明確になる。

### D. 実装ガイドライン

- **絶対パスインポート**: `@/*` 形式を徹底し、可読性を維持する (`tsconfig.json`)。
- **定数の一元管理**: ルーティングパス、UIテキスト等は `src/constants/` で管理する。
- **型定義の自動生成**: Supabase CLI を活用し、DBスキーマとフロントエンドの型を同期させる。
- **ファイルの冒頭にコメント**: コメントにはファイルのパスとそのコンポーネントの概要を記載すること。機能の追加や変更も概要に反映させること。
  1. **ファイルパス** (File Path)
  2. **アーキテクチャ設計方針** (Architecture)
  3. **利用規約** (Usage Guidelines)
- **GitHubのブランチとマージ**: 新機能を実装するときはブランチを都度分けること。動作確認が終了してdevelopへはMerge Commit (--no-ff)、mainへはSquash Mergeを行うこと。

## 4. データベースとセキュリティ

- **マルチテナント**: すべてのデータは `world_id` と `owner_id` で保護。
- **RLS (Row Level Security)**: DBレベルでのアクセス遮断を徹底。
- **スキーマ**: `docs/schema.sql` を正典とする。
